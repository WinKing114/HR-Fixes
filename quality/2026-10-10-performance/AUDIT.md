# HR Fixes 1.0.1-rc.1 历史审查

后续 1.1.0-rc.1 的新增兼容修复和验收见 [COMPATIBILITY.md](COMPATIBILITY.md)；以下保留当时版本的验证范围。

范围：实际安装的 Minecraft 1.20.1 / Forge 47.4.16 / `EternalStarlight-0.9.0-hotfix.jar`。目标二进制哈希见 `project.json`。发布候选的两个类与历史私有 1.0.0 编译结果逐字节一致；本轮未修改修复源码。

## 正确性与生命周期

实际目标 `ForgePayloadPacket.handle` 使用 `Context.enqueueWork`，其任务将 `getSender()` 传给 `SyncAttachmentsPacket.handle(Player)`。服务器发给客户端时 sender 为 null；原方法第 57 行立即访问 `player.level()`，尚未查找实体或解码附件便失败。原采样和基线运行证明这是真实路径。[Forge 的网络线程与 sender 语义](https://docs.minecraftforge.net/en/1.20.1/networking/simpleimpl/)。

注入位于该方法 HEAD：非空参数直接保留原实现；空参数且位于客户端主线程、已有本地玩家时，使用本地玩家重新调用原方法一次，并取消外层调用。第二次调用参数非空，不会递归注入。原方法依然按包内实体 ID 查找目标，既可更新附件，也可删除附件；没有改成仅更新本地玩家，没有捕获并吞掉解码错误。

没有本地玩家或非主线程时取消。实际 Forge 接收路径已经排队到主线程；Minecraft 的登录和重生处理也先进入主线程，在同一处理方法内建立 ClientLevel/LocalPlayer。常规登录、切换维度和重生不需要额外延迟队列。无玩家的退出阶段没有可应用附件的活动世界，丢弃该旧会话的数据比保留到后续世界更合适。补丁不持有包、不持有玩家或世界引用。

**没有通用补发保证。** 原模组在实体开始被跟踪时发送已存在的附件快照，附件变化时按自身 `shouldSync` 策略发送更新；这些原机制均保留。但不能宣称任意丢弃的数据都必定重发。若另一个模组在活动会话中主动造成无玩家窗口，或改变收包时序，本候选不承诺恢复该窗口的一次性数据；必须单独复现后再处理。原方法对目标实体不存在/未知附件的返回行为也未改动。

原 Forge 附件表是按实体整数 ID 索引的全局表，单人游戏客户端与内置服务器共享它。原测试只看到值变化不足以证明收包成功。本轮网络测试先设置相反的已存值，再只将期望值放入发送包，不把期望值写入服务器表，最后在客户端检查更新/删除。因此能区分网络接收成功与共享表造成的假阳性。删除包使用原 wire format 的 presence=false；测试反射只修改该临时测试包的数据字节，不修改目标 JAR。

本补丁不接管原模组的附件保存、死亡复制或全局表清理。外部专用服务器重新连接与不同服务器间实体 ID 重用的完整状态管理尚未实测，不据单人测试推断所有附件持久化正确。

## 兼容边界与独立性

- 稳定 ID：`hollowrealm_performance_compat`；显示名 HR Fixes；版本及文件名均为 1.0.1-rc.1。
- 精确 MC 1.20.1、Forge 47.4.16、客户端依赖 Eternal Starlight 内部版本 0.9.0。构建器额外核验审查过的目标二进制哈希；游戏加载器不核验该哈希。
- Mixin 指向精确 `handle(Player)` 描述符、`remap=false`、`require=1`；只列在 client 配置中。目标 API/语义改变后需重审；不自动适配其他同版本二进制。
- 入口类不引用客户端或目标模组类型；专用服务器不应用注入，不需要安装 HR Fixes。未执行专用服务器完整启动验收，发布定位为客户端。
- 缺少目标的独立客户端启动真实产生 Forge 必需依赖错误，阻止加载；不是假定其可选加载。
- JAR 只有两个自有类、模组/Mixin/资源包元数据和 MIT 许可证，无第三方代码、素材、运行诊断脚本或网络通道。
- Java 17 编译，候选在现有 Java 21 客户端运行。不同 JVM 的完整运行行为未另行承诺。
